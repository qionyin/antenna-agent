# 多 Agent 上下文压缩 A/B 测试

## 测试范围

- 模型：`gpt-5.5`
- 测试问题：100 条唯一运行日志问题
- 难度分布：简单 34 条、中等 33 条、复杂 33 条
- 裁决分布：pass 60、revise 15、block 10、reroute 10、wait_user 5
- 调用次数：100 问题 × 4 Agent × 2 方案 = 800 次
- 成功调用：800；失败调用：0
- 总耗时：518.32 秒
- Redis 记忆：L2 事实 3 条、L3 工作流 1 条

100 条问题来自项目任务日志。由于历史日志中包含自动测试和边界任务，不能将它们全部称为
真人线上问题。标准答案使用人工定义的结构化场景标签，覆盖正常推进、修改、阻塞、重路由和
等待用户，不使用另一个模型给当前模型打分。

整体结果：

```text
准确率：100.00% -> 99.75%
Prompt Token：2,589,616 -> 2,232,897，节省 356,719（13.78%）
总 Token：2,613,033 -> 2,245,907，节省 367,126（14.05%）

```

API 自检发现 `cached_prompt_tokens` 会在 4608 和 5632 等数值之间变化，并非固定前缀。因此没有
采用 `prompt_tokens - cached_prompt_tokens` 计算上下文大小。API 总 Token 仍按原始 `usage`
统计；实际上下文 Token 则直接对发送内容分词，两者分开报告。

## 压缩策略

```text
task subagent
  当前步骤 + Top2 相关 L2 事实

module reviewer
  当前产物 + 当前步骤

global reviewer
  当前产物 + 最新模块审查 + Top1 相关 L2 事实

central agent
  当前计划 + 最近6条对话 + Top2 L2事实 + Top1 L3工作流
```

## 唯一偏差

`context-047`：`patch antenna GWO optimize S11`。

标准裁决为 `pass_next_step`，压缩后的中枢返回 `complete_task`。任务、模块审查和全局审查均
正确。说明中枢仅读取当前计划时，需要进一步明确“当前步骤通过”和“整个任务已经完成”的
边界；不能只依据当前步骤为 `passed` 就判断任务结束。

修正仅收紧当前步骤的输出约束：删除 `complete_task`，明确 `passed -> pass_next_step`，不新增
任务完成判断。针对原失败样本重新调用后返回 `pass_next_step`，与标准答案一致。原始100条
统计仍保留为修正前结果，没有用单条复测覆盖原始统计。

## 结论

该策略在结构化多 Agent 裁决中值得继续：总体准确率仅下降 0.25 个百分点，总 Token 减少
14.05%，平均响应时间降低 13.84%。但目前只测试了 3 条 L2 和 1 条 L3 真实记忆，也没有衡量
自由文本回答质量。正式接入前应先给中枢增加明确的任务完成条件，再用更大的长期记忆库做
一次压力复测。
